# M2.5 — Areas and their loot tables: the build plan

**Status: SIGNED OFF 2026-08-31 — plan as written, plain-line loot table,
FK item references with the config block removed, publish minimum as
proposed. ONE deliberate deviation from the recommendation, at the Lead
Developer's choice: click-on-the-image spot placement ships DAY ONE, as a
vanilla-JS enhancement over the number fields — which stay as the
keyboard-and-no-JS way (the M11 decision's rule: placing works by tapping
AND by keyboard, dragging/clicking never the only way).**

The build plan's M2.5 is "bulk entry for tables" — loot tables will one day
be hundreds of rows, and one-row-at-a-time web forms are where projects
like this stall. This plan proposes the editor AND the move that makes it
possible: exploration areas leave the config file and become data. It also
quietly delivers most of the Lead Developer's 2026-08-31 ask — areas
editable as a whole (background, spots, loot) — without touching the
parked design question (the MECHANIC already works; this is content
editing). CLAUDE.md §7's three questions are answered below.

---

## 1. What exists today

- ONE area (whispering-wood), living entirely in `config/config.php`:
  name, description, five clickable spots (x/y percentages), five weighted
  loot rows (types: nothing / item-by-SLUG / creature).
- The scene's background is a CSS gradient placeholder — no art anywhere,
  though the art store's "Area background" kind has waited for this since
  M2.2.
- The config seam is narrow: the controller takes the areas map, the
  service only ever reads `$area['loot']`, and one loop in the front
  controller collects loot slugs for the item editor's "woven in" lines.
  `exploration_visits` already references areas by slug string, so player
  history survives the move untouched.
- A fragility worth naming: an empty loot table (or all-zero weights)
  would crash the reward roll. Config written by a careful developer never
  hit it; an editor MUST make it impossible.

## 2. What M2.5 builds

### The data (one migration — named in the handover's first paragraph)

- **`areas`**: slug (minted once, never editable — `exploration_visits`
  holds slugs), name, description, `background_art_id` (FK → art_files,
  SET NULL), `status` (default 'published', same seeds-stay-live reasoning
  as everywhere), `updated_at`. The migration seeds whispering-wood from
  today's config, byte for byte.
- **`area_spots`**: area_id (CASCADE), x, y (0–100).
- **`loot_entries`**: area_id (CASCADE), `type` (allow-listed in PHP:
  nothing / item / creature), **`item_id` (FK → items, RESTRICT)** — a
  real reference instead of a typed slug, so "loot pointing at a mistyped
  item" becomes impossible to WRITE, not just gently survived. Plus
  weight (≥ 1, enforced), message, sort_order.
- The config's `areas` block is REMOVED in the same change — one source of
  truth. `gameplay.exploration` keeps only the mechanics knobs
  (clicks_per_visit, window_seconds), which stay config because they are
  tuning, not content.
- The item editor's "woven in" lines and the M2.4 reference loop read the
  new tables instead of config.

### The editor (Artist role, the familiar shape)

`/admin/areas` (list + start-a-draft) and `/admin/areas/{id}`, sections
with their own saves: words; the background from the art store (the shared
picker, Background shelf — the player scene keeps its cosy gradient as the
fallback until one is chosen); **the spots** as a small editable list of
x/y pairs (0–100, validated) — honest number fields first, click-to-place
on the image as a later enhancement, noted so it reads as chosen; and
**the loot table**, the heart of the increment:

**The live table, this site's way.** The current rows are shown as a
readable table, and edited/pasted as PLAIN LINES in one field — one row
per line, `weight; what; message`, where `what` is `nothing`, `creature`,
or an item picked by its address (`item: acorn-treat`):

    45; nothing;            Only leaves and a soft wind. Nothing this time.
    25; item: acorn-treat;  A crunchy little acorn, tucked under a root.
    15; creature;           Something small blinks in the undergrowth!

Saving validates every line and is **all-or-nothing with nothing lost**:
any bad line is named by number with a plain reason, the field keeps
exactly what was typed, the good lines wait with it. (The build plan's
"a malformed row is rejected without losing the rest", read as: the rest
of your TYPING survives — a half-applied table would be worse than a
second save.) Item addresses must exist; a draft item draws a warning, not
a refusal. At least one row, every weight ≥ 1 — the crash from §1 becomes
unwritable. Each save is one version (content_versions, type 'area',
snapshot incl. spots and loot), audited (five new Area* audit actions),
revertible.

Publish minimum: a name, at least one spot, at least one loot row.
Drafts are invisible to players: the area list and both area routes serve
published only. Unpublish allowed, same plain words as everywhere.

### The player-facing crumbs (principle (b2))

The area page draws its background art behind the scene when one is
chosen (gradient fallback stays); the area list shows it as the tile's
face. Nothing else changes for players — deliberately.

## 3. The three security questions

**1. Who, enforced how?** Artist/Owner via the AdminGate on every route
(matrix-tested), CSRF everywhere, the shared content-save rate limit.
Every value allow-listed or bounded: type from three words, weights and
coordinates integer-bounded, items by id-must-exist (FK beneath), message
lengths capped.

**2. Worst case from a hostile request?** Saving a loot table that crashes
the roll — unwritable (≥1 row, weights ≥1, service keeps its gentle
unknown-reward fallback as the belt-and-braces). Pointing loot at a
nonexistent item — refused at parse AND impossible past the FK. Hostile
text in messages/names — escaped on output, capped, script-tag test.
A draft area reached by URL — redirect, tested. Racing saves — the same
accepted versioned-and-audited last-write-wins as every editor.

**3. What do the tests refuse?** The bad line named by number with the
typed content preserved; empty table refused; zero weight refused;
unknown item address refused; coordinates out of range refused; draft
areas absent from the list and refused on both routes; publish refused
with missing pieces named; revert restores spots and loot; the item
editor still names loot references after the config move (the M2.4 test
keeps passing against the new source); the gate matrix grows every route.
Smoke: edit whispering-wood's loot through the real field, see the change
survive, explore the real area, put it back.

## 4. Slices

(1) Schema + migration + repositories + re-seaming (site behaviour
identical, every existing test green); (2) the editor; (3) the player-page
background + docs (`artist-guide-areas.md`) + smoke + shots. One handover.

## 5. Questions for sign-off

1. **The loot table as plain lines** (§2): one field, paste-friendly,
   all-or-nothing with per-line errors and nothing lost. The alternative —
   a grid of per-row form widgets — is clickier to build and worse to
   paste into. OK?
2. **Spots as number pairs first**, click-on-the-image placement as a
   later enhancement?
3. **Loot by real item reference** (picked address, FK underneath) and the
   config areas block removed — one source of truth?
4. **Publish minimum**: name + ≥1 spot + ≥1 loot row; background optional
   (the gradient stays as the fallback)?
