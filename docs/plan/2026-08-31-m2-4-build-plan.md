# M2.4 — The item and shop editors: the build plan

**Status: SIGNED OFF 2026-08-31, all four questions decided as recommended:
the re-scoping (postcards → M6, themes → M4) is real and recorded in
decisions.md + an inline note in felkyo-build-plan-2.md; categories stay a
manual recipe until M4; one `content_versions` table with the species
history migrated in; slugs immutable / no deletion / retire = draft.
BUILT the same day; as-built notes: the art picker became one shared
template (`admin-art-picker`, the species editor's own picker being its
older twin), the shopfront header is `partials/shopfront.php`, and the
smoke test found one real bug before any human did — an item that is
several things at once (starter gift AND loot) lost all but one of its
reference lines.**

The build plan's M2.4 names four editors: items, shops, postcards, themes.
This plan proposes building **two** of them now and moving two to the
milestones that own their content — a re-scoping that needs your explicit
yes, because it amends the plan (the questions at the end). The three
security questions of CLAUDE.md §7 are answered below.

---

## 1. What the survey found, honestly

- **Items have no write layer at all.** Every item that exists was written
  by a migration; there is no ItemRepository, no draft state, no versions.
  Item pictures are a convention path into a folder that does not exist —
  every item today renders its category's icon placeholder. (The art store
  already reserved the `Icon` kind for exactly this.)
- **Shops are four columns** (slug, name, description, created_at). The
  shopkeeper Ruinily exists only as two hardcoded strings; there are no
  background, portrait or dialogue columns. The seasonal
  `available_from/to` columns on shop listings exist (decided 2026-08-12)
  and nothing reads them yet.
- **Postcards and themes exist nowhere as data** — no tables, no classes,
  no templates. M6 already decides what a postcard IS ("cards are items
  bought from a shop… a piece of art carrying a fixed pre-authored
  message"), and M4 decides what a theme is (selectable palettes, with
  contrast checked as you pick).
- **Two slug couplings** would break silently under careless editing: the
  starter treats (`acorn-treat`, `honey-treat`) and the exploration loot
  tables reference items by slug.

## 2. The re-scoping proposal (question 1)

**Build now: the item editor and the shop editor** — both have live player
mechanics that benefit the same day, and the shop editor is what the Lead
Developer asked for in words (decisions.md 2026-08-31).

**Move: postcards to M6, themes to M4.** Not dropped — RE-HOMED, and here
is the reasoning to judge: principle (b2) says a content type ships with
its panel screen *in the same milestone as the content type*. Postcards
become content in M6 (which defines them as items-with-a-fixed-message —
pre-building a separate postcards table now would likely be rework);
themes become content in M4 (whose editor must be built around the
automatic contrast check — a colour editor without that guard is the exact
tool that ships an unreadable page). Building either editor now means
inventing the content type ahead of its design, which is what the forms
deferral (M5) already declined once, with sign-off.

## 3. What M2.4 builds

### The item editor

- **Migration**: `items` gains `status` ('draft'/'published', default
  'published' — same reasoning as species: seeds and fixtures stay live,
  the panel creates drafts explicitly), `updated_at`, and `icon_art_id`
  (FK → art_files, SET NULL). Plus one **`content_versions`** table —
  see §5.
- **The draft asymmetry, again**: anything a player already OWNS keeps
  working (inventory, feeding, selling read unfiltered), but a draft item
  is not on any shelf and cannot be bought (the shop listing and the
  purchase-time lookup both filter `status='published'` — each with its
  refusal test).
- **One page per item**: name, description, price and sell value (the 80%
  margin rule enforced AT SAVE with a plain sentence, not only by the test
  suite), happiness/energy bonuses (what makes something a treat), the
  category as radio tiles, the icon from the art store (`Icon` shelf, with
  the two-source resolver pattern from species: art-store picture, else
  the convention path, else the category icon — nothing existing changes
  until an icon is chosen), and this item's shelf listing (on the shop —
  see below). Versions and restore, publish/retire — identical shape to
  the species editor, because the artist should have to learn it once.
- **Slugs are minted at creation and never editable; deletion is not
  offered.** This is the guard for the two couplings above: a slug the
  starter grant or a loot table names can never be renamed or deleted out
  from under them. Retiring an item = back to draft (off the shelves;
  owned copies keep working). The editor SHOWS where an item is referenced
  (starter treats, loot tables, shelves) so "why can't this go?" is
  answered on the page.

### The shop editor, and the shop page it feeds

- **Migration**: `shops` gains `keeper_name`, `keeper_greeting` (the line
  under the shop's name), `keeper_refusal` (the "nothing like that on the
  shelves" line — replacing the hardcoded Ruinily string), `background_art_id`
  and `portrait_art_id` (FKs → art_files, SET NULL), `status` (default
  'published'), `updated_at`. A data migration seeds Ruinily as the
  general store's keeper with today's exact refusal line, so nothing
  changes until somebody edits it.
- **One page per shop**: name, description, the keeper (name, greeting,
  refusal, portrait from the `Portrait` shelf), the background (from the
  `Background` shelf), and **the shelves**: the offerings list — add an
  item (published items only, searchable tiles), remove one, and each
  listing's optional from/to dates, which brings the 2026-08-12 seasonal
  columns to life exactly as that decision described (a blank date means
  always; out-of-window items are simply not offered).
- **The frontend surfaces ship in the same increment** (principle (b2),
  and the Lead Developer's explicit ask): the shop page's header shows the
  background art behind it, the keeper's portrait and greeting beside the
  name, and the refusal line comes from the shop's own words. The shop
  listing query starts honouring the dates. `/shop` keeps meaning the
  general store; more shops get their own doors in M9, but a second shop
  built in the panel is already complete data the day M9 routes to it.
- Slug immutable, no deletion, draft = invisible-to-players (moot today
  with one shop; load-bearing the day M9 lists shops).

## 4. The three security questions

**1. Who may, enforced how?** Artist or Owner, via the same AdminGate on
every route (the matrix test grows every new route); CSRF on every form; a
shared `rate_limit_content_save` for both editors. Values validated against
allow-lists: category by id-exists, art by id-exists AND right kind, dates
as real dates with from ≤ to, status two words, prices bounded integers.
The 80% margin rule is checked at save against the config number.

**2. Worst case from a hostile request?** Buying a draft (blocked at the
purchase-time lookup, not just the listing — tested); selling an item to
the shop above its margin (refused at save AND still pinned by
`ItemSellValueTest`); linking art of the wrong kind (refused, same as
species); a shelf listing pointing at a draft or missing item (add-to-shelf
validates published-and-exists; the SET NULL / RESTRICT keys hold beneath);
hostile text in names/descriptions/keeper lines rendered on public pages
(escaped on output everywhere, lengths capped, a script-tag name test);
date games (from > to refused; nonsense dates refused); racing saves (same
accepted trade as species: last write wins per section, every save
versioned and audited, nothing lost).

**3. What do the tests refuse?** A draft item absent from the shop page
and refused at purchase; a draft shop invisible in any listing path; the
margin refusal at save; wrong-kind art refused; from>to refused; a listing
outside its dates not offered (and offered inside them); removing a listed
item's category refused (RESTRICT); the gate matrix on every new route;
script-tag names inert; versions restore both editors; every action
audited. Smoke test: edit the general store's keeper through the real
form and see the greeting on the real shop page; create an item, watch the
shop refuse the draft, publish, buy it, sell it back within margin.

## 5. One undo system, not three (question 3)

The species editor built `species_versions`. Items and shops need the
same. Three parallel version tables would be the second copy of the same
code the build plan forbids — so M2.4 builds **`content_versions`**
(`content_type`, `content_id`, `snapshot` JSON, `saved_by_user_id`,
`created_at`), moves the existing species snapshots into it in the same
migration, and retires `species_versions`. One repository, one prune rule
(newest 20), three editors on it — and every future M2 editor free.

## 6. What stays manual, on purpose (question 2)

**Item categories.** Adding one today means adding a colour token to
`theme.css` and an SVG symbol to a template — FILE edits a panel must not
perform. Making categories panel-editable means moving colours and icons
into data, which is exactly the machinery the **M4 theme editor** must
build anyway (colours as data + the automatic contrast check). Categories
change rarely (eight, stable, seeded from the design doc); the written
recipe stays until M4 gives them a proper home. Deciding otherwise means
building a slice of the theme system early, without its contrast guard.

## 7. Files, scale, slices

The species editor's shapes are copied deliberately: repositories gain
writes; `ItemEditorService` / `ShopEditorService` own the rules with the
same `withHistory` trace shape; controllers are the same
gate→CSRF→limit→service→flash pattern; templates reuse the panel's cards
and radio tiles. Slices: (1) items end to end; (2) shops + the frontend
surfaces + seasonal dates; (3) the two docs recipes
(`artist-guide-items.md`, `artist-guide-shops.md`) replacing
`adding-items.md`'s manual half. One handover, one migration —
**named in its first paragraph, as always.**
