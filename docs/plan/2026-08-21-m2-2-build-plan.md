# M2.2 — Image upload: the build plan

**Status: awaiting sign-off. No code has been written.**

The *where* is decided (`2026-08-21-m2-2-where-files-live.md`: a Railway
volume, 5 MB / 2048×2048, GIF/PNG/WebP, animated files kept byte-for-byte).
This is the *how* — the mandatory written plan of CLAUDE.md §7, because
uploads are "the highest-value target on the site". It answers the three
security questions before anything is built.

---

## 1. What M2.2 builds

The upload **engine**, and one small panel screen to drive it, so that M2.3
(one page per creature) can attach pictures to species without inventing
upload on the spot.

**In scope:**

1. **`ImageStore`** (`src/Art/`): put / replace / delete / URL for a
   stored picture. One implementation — a folder on the volume — behind a
   small interface, so R2 later is a second implementation, not a rewrite.
2. **`UploadedImage` validation**: reads the file's real bytes, not its
   name or the browser's declared type; refuses anything that is not a
   well-formed GIF, PNG or WebP; caps size and dimensions; detects
   animation; strips what metadata can be stripped without touching
   pixels (see §4).
3. **An `art_files` table** (migration — **the handover names it in its
   first paragraph**): one row per stored picture — generated name, kind
   (sprite / icon / portrait / card / background / library, allow-listed),
   dimensions, size, animated flag, who uploaded it, when.
4. **Serving**: pictures live *outside* the web root and are served by one
   route (`/art/{name}`) that sets the content type from our own record,
   `X-Content-Type-Options: nosniff`, and a one-year immutable cache —
   safe because names are content hashes, so a *replacement* is a *new*
   name and old caches never show the old picture. That is M2.3's
   "one-click replacement that defeats caching", solved once, here.
5. **The Pictures screen** (`/admin/pictures`, Artist role — owner passes
   everything): upload a picture with its kind, see everything uploaded
   as a grid (thumbnail, kind, dimensions, size, "animated"), delete one.
   M2.3 will pick from this store per species. Same golden rules: tiles
   not dropdowns (the kind is chosen from radio cards), plain words,
   mobile-first, keyboard-reachable, visible confirmation.
6. **Named config values** (`config/config.php` → `art`): max bytes, max
   width/height, allowed kinds, total-volume warning threshold, and the
   storage path (env `ART_STORAGE_PATH`, falling back to Railway's
   `RAILWAY_VOLUME_MOUNT_PATH`, falling back to `storage/art` locally).
7. **Deployment guide**: the exact clicks to create the volume, mount it,
   set the variable, switch on daily + weekly backups.
8. Tests (§5), a smoke-test chapter, gui-shots of the new screen.

**Out of scope:** attaching pictures to species (M2.3), "is this picture
in use?" protection on delete (nothing references pictures until M2.3 —
that increment adds the guard the moment references exist), the
"download all art" maintenance button (M2.8).

## 2. Data flow, and how it scales

An upload is one request: PHP receives the file in a temp location,
validation reads it once (header parse, not a full decode for animated
files), the bytes are written to the volume under `sha256(bytes)` plus the
right extension, one `art_files` row is inserted. Serving is one indexed
lookup by name plus a `readfile()` — and with the immutable cache header a
browser asks for each picture **once**, then never again. At this site's
size (a few pictures per page, hundreds of pictures total) that is far
cheaper than a database query. If it ever needed to serve thousands of
pictures a second, the fix is R2 or a static-file rule in front of PHP —
the `ImageStore` boundary is where that change would land.

## 3. The three security questions

### 1. Who is allowed to do this, and how is that enforced?

Only staff holding the **Artist** role (or Owner) may upload or delete;
enforced by the same `AdminGate` every admin route goes through — role
read fresh from the database on every request, door confirmation and
second factor required — plus CSRF on both forms and a per-user rate
limit on uploads. Anyone may *view* a served picture: the whole site
displays them. Viewing is safe because the route only ever serves files
from our own `art_files` table by exact generated name, with the content
type we recorded — never a path, never a guessed type.

### 2. What is the worst thing a malicious user could do with this endpoint?

- **Upload something that is not an image** (a PHP file, an HTML page, a
  script called `sprite.gif`) — refused by reading the bytes: the file
  must begin with the exact GIF/PNG/WebP signature and parse as one all
  the way through.
- **Upload a "polyglot"** — a real GIF whose bytes are *also* valid
  script. Defeated twice: the volume is outside the web root, so nothing
  in it can ever be executed by the web server; and it is served with the
  image content type plus `nosniff`, so no browser will run it either.
- **Upload a decompression bomb** — a tiny file that declares enormous
  dimensions or thousands of frames, to exhaust the browser or the server
  that decodes it. Dimensions are read from the header and capped at
  2048×2048 *before* anything decodes the pixels; file size is capped at
  5 MB; animated files are never decoded on the server at all.
- **Escape the folder with the filename** (`../../.env`) — impossible: the
  browser's filename is never used for anything except a sanitised display
  label; the stored name is the content hash.
- **Fill the disk** — the volume has 5 GB; a 5 MB cap, an upload rate
  limit (proposed: 60 per hour per user) and a warning on the Pictures
  screen when the volume passes a configured threshold (proposed: 4 GB)
  mean an artist cannot fill it by accident and an attacker cannot fill it
  quickly — and only staff behind the door and a second factor can reach
  the endpoint at all.
- **Race two uploads of the same file** — the content-hash name plus a
  unique index on it make a duplicate a no-op, never two rows.
- **Delete somebody else's picture** — deletion is by our own id, checked
  to exist; any Artist may delete any picture (the artist team is small
  and shared — this is a shared cupboard, not personal property), and
  every delete is audit-logged with the picture's details. In M2.3, a
  picture in use by a species refuses deletion.
- **Serve a stale or wrong picture after a replacement** — impossible by
  construction: a replacement has a different hash and therefore a
  different URL.

### 3. What does the test suite prove about the above?

Each refusal explicitly:

- A PHP script renamed `.gif`, an HTML file renamed `.png`, and a
  truncated real image are all refused; a real GIF, PNG and WebP are
  accepted.
- A valid GIF that is also valid JavaScript is accepted (it *is* a GIF)
  and served with `image/gif` and `nosniff`.
- A file over the size cap is refused; a real image whose header declares
  more than 2048 pixels on either side is refused *without* being decoded.
- A hostile original filename (`../../x`, null bytes, 300 characters) can
  neither escape the folder nor crash the display label.
- The served route refuses a name that is not a known hash (404, no path
  logic ever runs), and every successful response carries the expected
  content type, `nosniff`, and immutable cache headers.
- Animated GIF/WebP: detected as animated, stored byte-identical
  (hash of stored file equals hash of upload), and the comment / XMP /
  EXIF blocks are gone while the frames and loop block are intact.
- Still PNG: re-encoded, metadata gone, pixels identical.
- Every non-Artist, non-Owner role refused on the Pictures routes (added
  to the AdminGate matrix); CSRF omission refused; the upload rate limit
  refuses the 61st.
- Uploading the same bytes twice yields one row.
- Upload and delete each leave exactly one audit entry.
- Smoke test: log in as the owner, upload a real animated GIF through the
  real form, see it in the grid, fetch it by its URL and check the headers,
  delete it.

## 4. Animated files kept byte-for-byte — the risks, honestly

Re-encoding an animated GIF or WebP through PHP's image library keeps one
frame and throws the rest away, and CLAUDE.md forbids ever baking a static
frame from an animated source. So animated uploads are validated
structurally and stored as uploaded. What that leaves, and what is done
about each:

| Risk | What it really means | What we do |
|---|---|---|
| **Metadata inside the file** | GIF and WebP can carry comment blocks, XMP or EXIF — text an export tool wrote (software name, sometimes an author note). GIF has *no* GPS-style EXIF; WebP can. | The GIF/WebP block structure lets us **remove those blocks without touching a single frame** — a chunk-level strip, losslessly. So "byte-for-byte" means pixels, timings and loop count; comment/XMP/EXIF blocks are dropped. The loop block (`NETSCAPE2.0`) is kept — it is what makes the animation loop. |
| **A decoder bug in a browser** | In theory a malformed file could trigger a bug in a browser's GIF decoder. Real, and extremely rare, and only reachable by someone who already holds an Artist account behind a password and a second factor. | Structural validation (every block well-formed, ends properly, dimensions in range) rejects malformed files; we do not attempt to be a browser. |
| **Polyglots** | A GIF that is also script. | Served as an image with `nosniff`, from outside the web root. Inert. |
| **Frame bombs** | Many large frames make a browser work hard. | Dimension cap from the header; size cap. At 5 MB and 2048², the worst case is a slow page, not a broken one. |

**What Skerro needs to consider when exporting** (this becomes
`docs/artist-guide-pictures.md`, written for him, no code words):

1. **Export at the creature's native pixel size.** Do not upscale — the
   site scales pixel art by whole multiples itself and keeps it crisp;
   an upscaled export scales *again* and blurs.
2. **Set the animation to loop forever.** The site cannot fix a GIF that
   was exported to play once — without re-encoding, the loop setting *is*
   the file's. In most tools this is "loop: forever / infinite / 0".
3. **Keep frame delays at 20 ms or more.** Browsers treat delays below
   about 20 ms as 100 ms, which makes a "fast" animation suddenly slow;
   50–100 ms per frame is the usual pixel-art range.
4. **Use real transparency, not a matte.** A transparent background in the
   export shows the parchment through; a baked white or black square does
   not, and the site cannot remove it.
5. **Stay within 5 MB and 2048×2048.** Backgrounds at full page width fit
   comfortably; a sprite is a few hundred KB at most.
6. **GIF is 256 colours per frame; WebP is not.** For a sprite with a
   painterly palette, animated WebP keeps the colours and is smaller. Both
   are accepted and treated identically.
7. **Don't put notes in the file's comment field** — it is removed on
   upload anyway. The place for a note about a picture is the panel.
8. **Keep your originals.** The volume is backed up, but the source files
   (layers, palettes) exist only where the artist keeps them.

## 5. Proposed numbers (for sign-off)

| value | proposal | why |
|---|---|---|
| `art.max_bytes` | 5 MB | signed off in the memo |
| `art.max_dimension` | 2048 px | signed off in the memo |
| `art.allowed_types` | gif, png, webp | the formats the site already renders; JPEG has no transparency and no animation, so its absence is a feature |
| `rate_limit_art_upload` | 60 / hour / user | an afternoon of uploading a whole species is ~10 files; 60 is generous for people and slow for scripts |
| `art.volume_warning_bytes` | 4 GB | the Pictures screen says "the art disk is getting full" from here; the Hobby cap is 5 GB |
