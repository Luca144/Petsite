# M2.8 — Site settings and safe maintenance (build plan)

*2026-09-01. Proceeding under the standing arrangement (rough review
between increments; the full test round after M2.9).*

## What this builds

One screen for the Coder role (and the Owner): **Settings &
maintenance** — the game's tunable numbers editable with an explanation
beside each, and a SMALL FIXED SET of named maintenance buttons.
Tuning the game's feel must not need a deploy (build plan M2.8).

### Settings: a database override on top of config

Config stays the single place values are DEFINED and explained; the
panel writes OVERRIDES to a new `site_settings` table, and the front
controller lays them over `$config` right after the migration guard —
so every consumer (controllers, services) keeps reading plain config
arrays and nothing else changes.

**Only a fixed catalog is editable** (`SettingsCatalog`): each entry
names its config path, its type, its bounds, and its plain-words
explanation. The first catalog: registration open/closed, pet cooldown,
XP per pet, XP per level, gems per pet, the daily gem cap, exploration
clicks per visit, and the word blocklist (which may never be emptied).
Growing the catalog is adding an entry — never a free-form key editor.
Every setting shows whether it is the built-in value or a panel change,
and a panel change can be put back to built-in with one button.

### Maintenance: named buttons, and nothing else

- **Download every picture as one ZIP** — the art volume has NO platform
  backups (M2.2's honest note), so this button IS the backup story until
  further notice. Audited.
- **Clear the rate-limit slate** — for the day somebody locks themselves
  out testing. Requires a ticked "yes, clear it" checkbox (rule 9);
  deletes only throttle counters, never game data. Audited.

**No terminal, no command runner, no query console — ever** (build plan
M2.8: not negotiable, not to be revisited). A new need means a new named
button.

## The three security questions (CLAUDE.md §7)

1. **Who, and how enforced?** Role::Coder via `$adminGate->protect` on
   every route (Owner passes everywhere, as designed); all in the
   `AdminGateTest` matrix. Settings are the site's deepest knobs, so
   they sit behind the most technical role.
2. **Worst a malicious actor could do?** A hostile Coder is the surface:
   they can reopen registration or slow growth — visible, audited
   (before/after per change), reversible, and rate-limited
   (`rate_limit_settings`). They CANNOT: edit arbitrary config keys (the
   catalog is an allow-list in code), empty the blocklist (refused with
   the reason), set values outside each catalog entry's bounds, or run
   anything (no runner exists). The ZIP download leaks nothing players
   can't see — every stored picture is already served publicly by
   /art/{name}; the button only bundles them. Values are stored as JSON
   and re-validated through the catalog ON READ, so even a hand-edited
   database row cannot smuggle an out-of-bounds value into config.
3. **What do the tests prove?** The gate matrix refuses non-Coders on
   every route; a changed setting takes real effect (registration
   closed by override → the real register route refuses); out-of-bounds
   and wrong-type values are refused AT SAVE with nothing stored; the
   blocklist refuses to become empty; reset returns the built-in value;
   every change writes its audit row; clearing rate limits needs the
   ticked confirmation and actually clears; an out-of-bounds value
   planted directly in the table is ignored on read.

## Honest limits

- Settings apply on the NEXT request (they merge during boot). No
  caching layer — one indexed read of a tiny table per request.
- `.env`'s REGISTRATION_OPEN still sets the DEFAULT; a panel override
  wins over both. The settings screen says which source is live.
- The ZIP is built to a temp file and streamed; at the volume's 500 MB
  ceiling this is seconds, not minutes. If art outgrows that, the fix
  is chunked archives, noted here for later.
